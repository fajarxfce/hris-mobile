# Exact recipient destination proof

A retained canonical original now carries optional recipient provenance: the captured peer,
draft timestamp and next editor revision. Original ID, body and send timestamp already belong
to the immutable request. Together these values prove the exact recipient gesture after its
source queue has been retired. They do not prove transport delivery or current access.

The provenance remains inside the existing encrypted command request and its authenticated
terminal archive. Old schema1 requests omit the new field and remain readable. A canonical
legacy original cannot be retrofitted into a recipient acknowledgement. The current recipient
source describes plain text; reply, forward or edit metadata cannot be attached to that proof.

Submit first accepts an exact retained source without opening another ledger or reading later
typing. If the source is absent, it checks the exact canonical original before attempting a new
local handoff. After a handoff, it also checks the destination when recovery has already removed
the source. Matching retained facts confirm a lost storage response without creating another
message. Missing, unreadable or mismatched evidence does not fabricate success. Each lookup
retains the invocation's session/Group admission and cancellation ownership. No HTTP is involved.

The existing command repository atomically binds each ID to one immutable target. Tests use two
repository instances proposing different targets, verify one retained winner, and check that
replay cannot mutate ciphertext or wake acknowledged work. Additional cases cover encrypted
reopen, completed/cancelled archives, legacy encoding, exact nanosecond timestamps, later typing,
denial, account replacement, cancellation and lost replies. Eight policy and ten Submit methods
plus four storage methods run on desktop/browser. Actual app DI resolves the changed constructor.
Apple shared test source is compiled; new Apple runtime execution is not claimed.

This is a prerequisite for canonical transfer. There is still no consumer removing recipient
sources, no new product route, and no native delivery activation. Next coordinate one bounded
transfer through existing repositories, preserve independent canonical typing, and retire source
only after exact destination plus inbox GroupOriginal acknowledgement. Reuse pure index/repair
policies rather than calling another use case. Follow with pending-recipient inbox rows, explicit
rapid Send ownership, new-contact routing, complete company filters and explicit Group rollout.
Keep local transfer under the account/Group lifetime on Web as well as mobile: the existing
native recovery worker runs only on Android/iOS. The existing inbox repair owner already seeds
canonical originals, and seed with null repair can probe acknowledgement without writing. Trace
its changed-input ordering before introducing another owner or any scheduler retry.
