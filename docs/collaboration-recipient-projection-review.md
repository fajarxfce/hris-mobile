# Recipient projection after editor acceptance

Unapplied design review. The editor's provisional rows are not a substitute for a durable local thread projection. Before a product route opens, observe the exact recipient draft, its retained original submissions and later canonical association/history under the same admitted account/Group. Feed the latest retained submission timestamp into initial editor binding and acknowledge provisional rows only through exact immutable proof. The current ViewModel intentionally exposes no product route.

Raw APIs traced: ReplicaQuery supports an equality tag or one exclusive forward/reverse anchor, not an exact-ID selector. ReplicaStore.observeDocument already reads one published exact document with its checkpoint; workingDocuments is a bounded one-shot writer snapshot and may include staging/tombstones. observeQueries returns several indexed pages under one published checkpoint. Do not invent lexicographic sentinel anchors or alias peers to conversation IDs.

Recipient originals have a global128 quota and pages1..8; their existing IDs/tags do not include peer identity. A selected-recipient projection must not read all5,000 employee/draft rows. A bounded initial original inventory is an option to measure, but re-decrypting all128 originals on every keystroke or for several warm threads is avoidable. The authenticated source marker already separates original changes from typing. Consider an observation-scoped immutable cache of decoded original facts keyed by that logical version, while exact draft reads advance independently; this is replica data caching, not UI state. Validate coherent published snapshots, legacy missing-marker fallback, generation/account changes, mutable adapters, cancellation and no repeated reads on unchanged facts.

Alternatively extend the existing generic raw multi-query facility with a justified exact-ID read, preserving all old query behavior and executing under the same transaction. Such a foundation change needs real-storage coverage and a later proven Starter port. Do not add feature policy to datasources or force a format/tag migration merely to make an observer convenient. No option has been implemented or accepted yet.

Canonical association and list row/draft continuity remain separate unresolved requirements documented in collaboration-recipient-product-review.md. A visible-only merge or deletion of the recipient row cannot safely resolve independent later typing when an original transfers. Continue with explicit immutable identity and bounded reads before activating the new-contact route.
