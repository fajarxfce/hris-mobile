# Retaining a published client during admission renewal

Candidate under test, not accepted or installed. Release72's settled unready-recipient
capture has zero delivery transport retries but still13 device-setup reads,12 room
reads and six secret-storage-default-key reads in150seconds. The earlier instrumented
trace directly records admission expiry calling registry update/retire. Closing and
restoring the private SDK on ordinary freshness changes repeats native initialization.

`CollaborationRuntimeRetention.retainedForeground` describes one already published
foreground client. `foreground` still controls a new foreground reservation or promotion.
The registry cannot use retainedForeground to keep unfinished acquisition, promote a
background borrower, reopen a retired resource or bypass parent/company denial. Its
normal exclusive store reservations and disposal ownership remain unchanged.

The domain owner can retain that existing client through workspace/policy age only
while the same native parent and selected local owner remain valid and known company
permissions, modules, build requirements and availability allow it. A fresh request
still needs current admission; the Matrix gateway rereads authority before and after
provider exchange. Retention is neither a cached sending grant nor a new key setup.

Freshness, known future maintenance and native-parent expiry are separate monotonic
boundaries. An earlier policy expiry cannot discard a later maintenance timer. Clock
rollback and same-family token observation cannot extend either boundary. Selection
loss, actual denial, parent change and collector disposal still remove the client.

Focused tests and the full required checks must pass before source acceptance. Native
validation must use the existing private store and original waiting message, with no
replay, and measure idle SDK requests as well as delivery requests. No claim about the
separate71 Storage/IllegalStateException follows from fewer runtime replacements.
Automatic first-login activation and readiness events remain separate required work.
